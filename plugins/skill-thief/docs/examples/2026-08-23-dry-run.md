plan. It follows `skills/skill-thief/SKILL.md` literally, phase by phase,
against a real public source, and stops at the Phase 5 gate as instructed.
Nothing past this document was written as a result of the source's content:
Phase 6 was not run, and no verdict from the table below has been approved.

This document reflects a round-1 fix. An independent review of the first
version of this run found that two of the five gate-table rows mislabeled a

gap in the granularity ladder, and found a self-contradiction in
`references/host-discovery.md`. All three are fixed in
`skills/skill-thief/references/` and `skills/skill-thief/SKILL.md`; see
"Round 1 fixes" below for exactly what changed, and why the earlier version
was wrong.

and no changes are written before the approval gate.

## Phase 2: scouted mechanisms

Eight mechanisms extracted, restated in neutral vocabulary:

1. **explicit-skill-requests test suite** (`tests/explicit-skill-requests/`, `run-test.sh`, `run-haiku-test.sh`, `prompts/*.txt`) -> a trigger-accuracy eval harness: canned prompts dispatched to a live model via `claude -p`, asserting whether a skill's description caused it to trigger and whether the model acted before loading the skill.
2. **SessionStart hook + using-superpowers router skill** (`hooks/hooks.json`, `hooks/session-start`, `skills/using-superpowers/SKILL.md`) -> a session-start hook that auto-injects a router skill's full text into every session's context (branching per harness: Claude Code, Cursor, Copilot CLI), guaranteeing skill-routing awareness without depending on the model choosing to invoke a tool.
3. **Per-harness plugin manifest set** (`.codex-plugin/`, `.cursor-plugin/`, `.devin-plugin/`, `.hermes-plugin/`, `.kimi-plugin/`, `gemini-extension.json`, `scripts/sync-to-codex-plugin.sh`, `scripts/bump-version.sh`, `.version-bump.json`) -> one canonical body duplicated into nine per-harness manifest files, kept in sync by a declared file list plus a bump/audit script and a one-way sync-and-PR script to an external fork.
4. **`skills/systematic-debugging/CREATION-LOG.md`** -> a per-skill creation log, sibling to the skill body, recording the source material and design reasoning behind that skill's structure.
5. **`skills/verification-before-completion/SKILL.md`** -> a standing rule that no success claim is made without first running the actual verification command and citing its actual output.
6. **`.pre-commit-config.yaml`** -> the project's own local checks wired into a git pre-commit hook via the pre-commit framework, scoped by file glob, so they run automatically before a commit can land rather than depending on a contributor remembering to run them.
7. **`tests/claude-code/analyze-token-usage.py`** -> a script that measures and reports the context-token cost of every installed skill's frontmatter, to make cross-skill routing budget visible.
8. **Root `CLAUDE.md` / `AGENTS.md` / `GEMINI.md` carrying contribution rules** -> stating repo-contribution verification requirements (which commands must run, and that their output must be cited) in prose a contributing agent will actually load, not just documented as available commands.

### Already-stronger list

host already has. Per the guardrail in `references/granularity-ladder.md`
("never record an already-implemented idea as rejected"), they are recorded
here rather than as Reject rows in the gate table below.

- **Mechanism 3 (per-harness manifest duplication + sync script)**: the host
  already solves cross-harness portability without duplicating files.
  README.md's "Install (other harnesses)" section states the skill body is
  "written harness-neutral on purpose, no scheduler tokens, no
  harness-specific tool names, no unguarded platform path variables, so the
  same files that ship in the plugin work as a plain copy," and
  `scripts/validate.mjs`'s `checkNeutrality` function enforces exactly that,
  confirmed passing in this run (`node --test` reports "the real skill body
  is harness neutral"). A single harness-neutral file is a stronger solution
  to the same underlying goal than nine manifests plus a sync/bump/audit
  pipeline, for a plugin this size.
- **Mechanism 4 (per-skill CREATION-LOG.md)**: the host already records
  design reasoning per structural decision, and does so at the repository
  level rather than the single-skill level this plugin ships. `docs/design/2026-08-23-skill-thief-design.md`
  records the spec's own provenance and decision table, and
  `docs/plans/2026-08-23-skill-thief-implementation.md` breaks the build
  into per-task steps with a "Self-review notes" section stating deviations
  and known gaps, both tracked and publicly readable in this repository.
  One log file per skill is a narrower record than a design doc plus a
  per-task plan, for a plugin this size.
- **Mechanism 5 (verification-before-completion rule)**: the host's own
  Phase 6 already states this, nearly verbatim: "Do not claim success
  generically; a report that says 'validation passed' without naming the
  command and its output is not distinguishable from a report that skipped

  add.

### Not-applicable-yet list

Mechanisms 2 and 7 were classified as Reject in the first version of this
run. Round-1 review caught that both fail the granularity ladder's own test
for a Reject (`references/granularity-ladder.md`: "would the stated reason
still hold if the host doubled in size or scope?"). Both reasons are about
this plugin's current size, not about the mechanisms themselves, so neither
belongs in a rejection record. They are recorded here instead, per the
ladder's corrected guidance.

- **Mechanism 2 (session-start router injection)**: not applicable while
  this plugin ships exactly one skill (`find skills -maxdepth 1 -type d`,
  one entry, confirmed above). The mechanism's entire value is
  disambiguating among competing skills at session start; there is nothing
  to route between yet. It would become a live finding if `skill-thief`
  ever grew to ship a second skill.
- **Mechanism 7 (cross-skill token-budget report)**: not applicable for the
  same reason. The mechanism's value is comparing frontmatter budgets
  *across* multiple skills; a one-skill plugin has structurally nothing to
  compare. It would become a live finding under the same condition as
  mechanism 2: more than one skill shipped here.

### Round 1 fixes

The first version of this run scored 5/5 on the criteria above and reported
"no prose fixes required." That report was wrong. Round-1 review found
three real defects, two of them in this run's own judgment and one in the
skill itself, and the "clean" grade papered over all three. Corrected here.

**Defect 1: two Reject rows were mislabeled deferrals.** Mechanism 2
(session-start router injection) and mechanism 7 (cross-skill token-budget
report) were both filed as Reject on the grounds that this plugin currently
ships one skill, so there is nothing to route between or compare across.
That reason is a fact about this plugin's current size, and it would stop
holding the moment the plugin shipped a second skill. The granularity
ladder's own guardrail bars exactly this ("a deferral is not a rejection"),
and the first draft violated it while using language ("not applicable to a
one-skill plugin") that should have been the tell. Fixed by moving both
rows out of the gate table and into a new "not-applicable-yet list," with
the condition each would need (a second skill shipped) stated plainly.
Mechanism 1 (live-model-dispatch eval) is a correct Reject and was left
alone: its conflict is with a stated project property (zero dependencies,
deterministic checks) that would hold regardless of the host's size.

**Defect 2: the granularity ladder had no home for a not-yet-applicable
mechanism.** The underlying cause of Defect 1 is not just a judgment error;
it is a gap in `references/granularity-ladder.md`. The ladder's guardrail
said what Reject is not allowed to hold, but never said where a
scale-dependent mechanism should go instead, so the closest available box
(Reject) got used anyway. Fixed by adding a "When a mechanism isn't a
finding yet" section to `references/granularity-ladder.md`: it names the
failure mode, explains why none of the four verdicts fit a mechanism whose
relevance depends on a condition the host does not currently meet, and
gives the test used above ("would the reason still hold if the host doubled
in size or scope?"). This does not add a fifth verdict; it names an exit
from classification, parallel to the already-stronger list, so such
mechanisms are recorded without being forced into Reject. `SKILL.md`'s
Phase 3 and Phase 4 were updated to mention the not-applicable-yet list and
its test, and `references/findings-template.md` gained a "The
not-applicable-yet list" section alongside "The already-stronger list" so
there is a place in the actual output document to record these.

**Defect 3: `references/host-discovery.md` contradicted itself.** One
sentence told the reader to "name where [a verdict home] would go" for an
absent rejection record; another, three paragraphs later, said to "never
invent a location for a surface that is not there." The first version of
this run followed the first sentence and produced `docs/rejections/` as a
proposed target, a path nothing in this repository actually suggests. Fixed
by removing the "names where one would go" instruction from "Building the
verdict-target map" and tightening "When a surface is absent" to forbid any
proposed path, even one explicitly labeled "not yet created," and to state
that Phase 6 decides the actual location if and when a Reject is ever
approved. The Phase 0 map and the gate table above now reflect the
corrected rule: the Reject target says plainly that no location exists and
proposes none.

The interpretive question noted in round 0 (whether an already-stronger
mechanism still needs a Phase 4 gate-table row) is resolved by the same fix
that produced the not-applicable-yet list: both are exits from
classification before a verdict is forced, and `SKILL.md` Phase 3 now names
both explicitly as Phase-3 outputs in their own right.

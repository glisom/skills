# Rejection record entry template

One file per rejected concept. The rejection record exists so a durable "no"
survives past the session that made the call, and so the same idea does not
get re-proposed and re-litigated every time someone reads the same source
again.

## What was proposed

State the mechanism plainly, in the neutral vocabulary it was evaluated
under, not the source's marketing name. Name the source it came from and
point back at its pinned version, so the rejection can be traced to exactly
what was reviewed.

## Why it is rejected

The reason must be durable and concept-level: something that would still
hold if the team had unlimited time, unlimited attention, and no competing
priorities right now. Restate the two guardrails from
`references/granularity-ladder.md` before writing this section, because both
are easy to violate without noticing:

- **A deferral is not a rejection.** "We are busy this quarter," "not a
  priority right now," or anything that could change with scheduling does
  not belong here. If the real reason is timing, this is not a rejection;
  do not file it.
- **An already-implemented idea is not a rejection.** If the host already
  does what the source mechanism proposes, that is prior art, not a
  rejection. Filing it here poisons future lookups: a later reviewer reads
  this record, concludes the idea was tried and discarded, and never learns
  it is live and working. Point at where it already lives instead of filing
  it as rejected.

If the reason does not clear both guardrails, it does not belong in the
rejection record.

## What to do instead

State the alternative, if one exists: an existing mechanism that already
covers the need, a different verdict that was chosen for a related part of
the same source, or an explicit statement that nothing replaces this and the
gap is accepted on purpose. A rejection with no stated alternative should at
least say so explicitly, rather than leaving the reader to guess whether an
alternative was considered.
